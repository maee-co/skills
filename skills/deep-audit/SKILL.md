# /deep-audit — 敵対的監査思考

deep-think が論点を広げて統合するのに対し、こちらは**目標（悪用・故障）から逆向きに壊しに行く**。通常のデバッグ規律（再現 → 仮説 → 検証）の代替ではなく、「2 回失敗した」「原因不明」の難所で思考の質を一段上げる追加回路。

## --security（脆弱性・公開前監査）

順番を守る。手順 1-2 の列挙が浅いと以降すべてが浅くなる — 時間配分の 4 割をここに使う。

1. **資産と信頼境界の列挙**: 何を守るのか（データ・権限・ゲート・評判）。誰が入力を握るのか（ユーザー・外部 API・tool 出力・同期元）。境界を 1 枚のテキスト図にする
2. **攻撃面の網羅列挙**: 入力経路 / 権限とシークレット / 依存（lib・hook・CI） / 公開されるもの。「対象外」と切る場所も明示する（切った理由が監査の限界記述になる）
3. **攻撃木**: 攻撃者の目標（データ窃取・権限昇格・ゲート素通し・なりすまし）から逆向きに分解し、目標ごとに最短経路を 1 本引く
4. **前提反転**: 設計者の安全前提を列挙し、1 つずつ「これが偽だったら何が起きる？」を回す（例: 「permissions が空 = 最小権限」は反転で落ちる典型）
5. **時間軸攻撃**: レース・TOCTOU・初期化直後の窓・キャッシュ/伝播ラグ。「この判定はいつ評価される？その瞬間、状態は完成しているか？」
6. **重大度較正**: 実害シナリオ（誰が・何をすると・何が起きる）を書けたものだけ Critical/Major にする。信頼度（実在確度）は別軸。実害シナリオを書けない指摘は重大度を落とす
7. **出力**: 指摘 + 再現条件 + 修正推奨 + 実行順。**監査者は修正しない**（監査の独立性。「どう直すか」まで書いて「直さない」）

## --bug（原因不明・2 回失敗した難バグ）

1. **再現最優先**: 再現しないうちは仮説を立てすぎない。再現手順を最小化してから進む。再現しない場合は「再現条件の探索」自体を二分法の対象にする
2. **仮説格子**: 仮説を同時に 3 本以上立て、各仮説に「どの証拠が来たらこれが死ぬか」を先に書く。1 本に惚れ込むのが難バグ最大の敗因 — 格子を書けば惚れ込みが物理的にできなくなる
3. **反証実験**: 本命仮説を支持する実験ではなく、**最も速く仮説を殺す**実験から実行する。1 実験 1 変数
4. **二分法**: 時間軸（いつから壊れた → `git bisect`・変更履歴）と空間軸（入力/変換/出力/環境のどの層か）の両方で挟む
5. **3 層根本原因**: ①症状の機構 ②なぜ混入した（どの変更・どの前提） ③なぜ検出されなかった（どの検出器の盲点か）。③まで掘って初めて再発防止（テスト・hook・CI）が書ける
6. **修正後の独立経路検証**: 修正を実行した tool 自身の echo ではなく、**別経路**で実体を確認する（「直った気がする」を殺す）

## 共通の敵対規律（両モード・終了前チェック）

- [ ] **自結論への最短反例**: 「この結論を崩す最短の反例は何か？」を最低 1 回、本気で探したか
- [ ] **見なかった場所リスト**: どこを見ていないかを明示したか（網羅性は「見た場所」でなく「見なかった場所の申告」で測る）
- [ ] **self-report 不信**: tool の成功表示・テスト green・要約・自己の完了主張を証拠として扱っていないか（それらは「主張」。証拠は独立経路から）
- [ ] **stale 前提の確認**: 参照したドキュメント・過去の結論は現在の Issue/PR/コードの状態と一致しているか
